# System Design — Last-Mile Delivery Tracker

**Rate Calculation Engine**
The engine is isolated in `services/rateEngine.ts` as two pure functions: `resolveZone(area, zoneAreas)` and `calculateRate(input)`. No hardcode; all inputs come from DB tables the admin edits. For each order, the backend fetches `zoneAreas` (area→zone mapping), `rateCards` (4 rows: B2B/B2C × INTRA/INTER) and `codConfigs` (2 rows) once per request and passes them in. This makes the engine unit-testable without HTTP/DB mocks.

Flow: `resolveZone` does exact lower-cased match on `area` (pincode) against `zone_areas`; if not found it throws 400 `Area not mapped to any zone: <area>` — never silent default, so customer sees why preview fails and admin knows which area to map. After both pickup and drop zones are resolved, `calculateRate` computes volumetric = (L*B*H)/5000, billable = max(actual, volumetric), zoneRel = pickupZoneId===dropZoneId ? INTRA : INTER, looks up rate where orderType+zoneRel match (throws 400 if admin forgot a card), computes base = billable*rate, then COD surcharge: if paymentType===COD, look up codConfigs for orderType — FLAT adds value, PERCENT adds base*value/100. It returns a structured breakdown (pickupZone, dropZone, volumetric, billable, zoneRel, rateApplied, baseCharge, codSurcharge, total) that the frontend renders before confirm. Example: B2C COD 100001→200001 (INTER, rate 80) with 20×15×20 (vol 1.2) actual 2 → billable 2 → base 160 + 10% 16 = 176. Tests cover intra/inter, vol>actual vs actual>vol, B2B 40/70 vs B2C 50/80, COD flat vs percent vs prepaid, and unmapped error — all without hardcode grep.

**Zone Detection Approach**
Zones are admin-created (`zones` table) and areas map many-to-one (`zone_areas` unique area). The customer enters free-text pickup/drop area strings which must exactly match a mapped area; the service normalizes to lower-case trimmed. If either side is unmapped, the preview endpoint fails 400 with the specific area, preventing silent fallback to a default zone that would misprice. INTRA vs INTER is decided solely by `pickupZoneId === dropZoneId`. This is simpler and more audit-friendly than geo-distance for this evaluation (no lat/lng needed), but the schema leaves `currentZoneId` nullable and could be extended to lat/lng + haversine if needed. Indexes: `zone_areas(area)` unique ensures O(log n) lookup; `orders(pickupZoneId)` helps filter by zone.

**Auto-Assignment Logic**
Agent model is explicit: `status` AVAILABLE/UNAVAILABLE/ON_DELIVERY, `currentZoneId`, `activeOrderCount`. The pure function `autoAssign({pickupZoneId, agents})` filters to AVAILABLE, then to those whose currentZoneId equals pickupZoneId. If none in-zone, it returns `assignedAgentId: null` with reason `No available agents in pickup zone — unassigned for manual`, rather than silently assigning a far agent. Among candidates, it sorts by activeOrderCount then id (deterministic) — load-balanced, so orders don’t pile on one agent. This function is called automatically on order creation (if autoAssign flag true, default) and via `POST /orders/:id/auto-assign` for manual admin trigger, and also on reschedule for the new attempt (may pick a different agent). Manual `POST /orders/:id/assign` always works even if assignment would otherwise fail, letting admin override. After assignment, the agent’s activeOrderCount++ and status becomes ON_DELIVERY; on DELIVERED/FAILED it decrements and returns to AVAILABLE when 0. Fallback is explicit: unassigned orders appear in admin’s filtered view (status CONFIRMED) for manual assignment. Justification: zone-based is deterministic, easy to demonstrate in placement without geo math, and admin-configurable via agent’s currentZone.

**Failed-Delivery Handling**
Lifecycle is append-only: `tracking_events` (order_id, fromStatus, toStatus, actorId, actorRole, timestamp, notes) is source of truth; `orders.currentStatus` is denormalized for fast reads. Allowed transitions map is validated server-side (CREATED→CONFIRMED→ASSIGNED→PICKED_UP→IN_TRANSIT→OUT_FOR_DELIVERY→DELIVERED plus FAILED→RESCHEDULED→ASSIGNED); any invalid transition gets 400 unless `override:true` by ADMIN, which is still logged as an event with actorRole=admin and reason. When an agent posts FAILED with notes (required), the order becomes FAILED, tracking event is appended, and an email is enqueued to the customer. The customer portal shows FAILED and offers a date picker; POST /orders/:id/reschedule with `rescheduleDate` validates only FAILED can reschedule and customer owns the order, creates RESCHEDULED event, then re-runs the same `autoAssign` logic for the new date — this may select a different agent and logs a second ASSIGNED event with `Reassigned on reschedule`. If no agent in zone, it stays RESCHEDULED for manual. Throughout, every status change enqueues an email/SMS via `notification_log` with 3× exponential backoff, never blocking the status update — a failed email is retried and logged as FAILED after 3 attempts. The timeline shown to the customer is strictly the ordered `tracking_events` for that orderId, guaranteeing immutability.
